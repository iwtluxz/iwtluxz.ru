# Кабинет iwtxz: GitHub Pages + Supabase

Страницы сайта работают на GitHub Pages. Авторизацию, настройки пользователей и загрузку файлов обслуживает отдельный проект Supabase. Netlify для этой схемы не нужен.

## Подключение сервера

1. Создай проект Supabase.
2. В его SQL Editor выполни весь файл `supabase/setup.sql`.
3. В **Authentication → Sign In / Providers → Email** выключи **Confirm email**. Сайт использует логин и пароль, адреса вида `username@accounts.iwtxz.ru` — внутренние идентификаторы, письма на них не отправляются. Настрой минимальную длину пароля **8 символов**.
4. В `backend-config.js` укажи URL проекта и его **Publishable key**. Эти два значения предназначены для публикации вместе с сайтом. `Secret` и `service_role` ключи сюда не подходят и в исходниках храниться не должны.
5. Отправь изменения в репозиторий GitHub Pages. Отдельная сборка для работы страницы из корня репозитория не требуется.

У проекта уже заполнены публичные настройки Supabase, предоставленные владельцем. После загрузки исходников на сайт браузер обращается к этому серверу напрямую. Отсутствующие `/api` на GitHub Pages больше не используются.

Доступ к данным проверяется в PostgreSQL: владелец видит свой черновик, посетители видят только опубликованный снимок. Логин привязан к аккаунту на сервере; отправка чужого `owner` или `id` не позволяет изменить чужую страницу. Правила Storage разрешают загрузку только в каталог собственного пользователя.

## Первый аккаунт владельца iwtlu

Логины существующих страниц защищены от свободной регистрации. В SQL Editor проекта выполни:

```sql
select private.issue_owner_claim('iwtlu') as owner_code;
```

Сохрани полученный код. Он действует 24 часа, используется один раз и не должен попадать в GitHub. На сайте выбери **Регистрация**, введи логин `iwtlu`, придумай пароль и вставь код в поле **Код владельца страницы**. После регистрации код удаляется из метаданных пользователя; сервер хранит только его хеш.

Аналогично выдаются коды для `shakzy` и `strelokk`. Логин `strelok` автоматически соответствует `strelokk`. Коды нужны только при первоначальном создании владельца: в дальнейшем вход выполняется обычным логином и паролем.

## Настройки страницы

- Ник, название вкладки, описание и надпись экрана входа.
- Аватар, размер аватара, фон картинкой/GIF или видео, затемнение, цвет и шрифт.
- Музыка, название трека, обложка и повтор. В превью работают воспроизведение, пауза, перемотка и громкость.
- Discord, Telegram, Steam и видимость карточки Discord.
- Смена пароля аккаунта.

Изображения: PNG/JPG/GIF/WebP. Фон также поддерживает MP4/WebM. Музыка: MP3/OGG/WAV/M4A/WebM. Максимальный размер файла — **4 МиБ**. Для более крупных файлов можно указать прямую HTTPS-ссылку. Новые загрузки получают уникальные URL, поэтому предыдущая версия картинки или трека не мешает обновлению из-за кэша.

Для файлов, заменяемых прямо в репозитории, `npm run version:assets` обновляет версии ссылок по содержимому. Эта же проверка добавлена в существующий GitHub Actions workflow синхронизации профилей.

**Сохранить черновик** сохраняет настройки только для владельца. **Применить к странице** публикует отдельный снимок. Последующие изменения черновика не меняют публичную версию до повторного применения.

Адрес нового профиля имеет вид `/profile.html?u=username`: такой адрес работает на GitHub Pages без серверных перенаправлений. Существующие страницы `/iwtlu`, `/shakzy` и `/strelokk` также подхватывают опубликованные настройки владельцев.

Загруженные медиа доступны по публичному URL с непредсказуемым именем. Черновики и список аккаунтов не являются публичными. Применение настроек страницы не создаёт коммитов в GitHub.

## Локальный просмотр

Из папки проекта в PowerShell:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/start-local.ps1
```

Открой `http://127.0.0.1:4173`. Скрипт использует Node.js 20+ либо встроенный Node в установленном VS Code. Терминал должен оставаться открытым; Ctrl+C остановит сервер.

Если Node.js доступен в PATH, можно запустить `npm run dev`. `npm run build` собирает публичные файлы в `dist/` для проверки или другого статического хостинга; закрытые локальные данные и `.env` туда не копируются.

**Локальный интерфейс с заполненным `backend-config.js` использует тот же Supabase-проект**, что и опубликованный сайт. Приватные ключи и пароль базы для просмотра не нужны.

В проекте оставлен изолированный локальный HTTP API для прежних тестов. При пустой конфигурации Supabase он доступен только на localhost и хранит данные в игнорируемой папке `.local-data/`. Его старые параметры `BUILDER_OWNER_USERNAME` / `BUILDER_OWNER_PASSWORD` относятся только к этому локальному режиму, не к аккаунтам Supabase.

## Отправка через GitHub Desktop

Текущая папка уже содержит историю Git и remote `https://github.com/iwtluxz/iwtluxz.ru.git`. В GitHub Desktop выбери **File → Add local repository** и укажи эту папку. После подготовленного коммита кнопка **Push origin** отправит изменения.

Не включай в коммит `.env`, `.local-data`, `node_modules` и `dist`: они исключены из Git. Удаления файлов, которые есть на GitHub, но отсутствовали в скачанной ZIP-копии, не относятся к изменениям кабинета.

## Проверки

```text
npm run test:backend-client
npm run test:builder
npm run build
```

Тесты браузерного адаптера проверяют контракт Supabase, права доступа, работу с ошибками и загрузками с подставным SDK. Старые HTTP-тесты используют отдельный локальный сервер и временное хранилище. Они не создают пользователей в настоящем Supabase-проекте.

Миграция дополнительно проверена на PostgreSQL-совместимом движке: регистрация, одноразовые коды, изоляция аккаунтов, разделение черновиков и публикаций, ограничения файлов и неизменяемость логинов. Проверка реальной облачной работы выполняется отдельно после подключения проекта.
